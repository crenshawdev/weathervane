    Per D-05 and PATTERNS.md, modify `src/location.rs::detect_location()` (currently lines 100-127) to insert a range guard immediately after the existing `if let (Some(lat), Some(lon)) = (data.lat, data.lon)` arm opens (currently line 107). The guard runs before the existing `let country = data.country.clone().unwrap_or_default();` line.

    Predicate: reject when the inverse of `(-90.0..=90.0).contains(&lat) && (-180.0..=180.0).contains(&lon)` holds. The `RangeInclusive::contains` implementation on `f64` uses `PartialOrd`, which returns `false` for any comparison involving NaN by IEEE 754 ordering semantics — so `(-90.0..=90.0).contains(&f64::NAN)` is `false` and the predicate also rejects NaN and infinity. Do not write the predicate as `lat <= 90.0 && lat >= -90.0` — that form is true-for-NaN and would silently re-admit malformed coords. The negated `contains` form is intentional and documented inline by a brief comment ("range-contains rejects NaN and infinity by IEEE 754 ordering").

    On the reject branch emit `tracing::debug!("detect_location: coordinates out of valid range");` (lowercase, no PII, no coord value in the format string), then return `Err(Error::LocationDetection)`. Do NOT log the rejected `lat` or `lon` values — the CLAUDE.md "no PII in errors/tracing" contract applies; the operator does not need the numeric value to act on the log.

    Do not extract a `pub(crate) fn valid_coords()` helper. The predicate is inlined per D-05; extraction is deferred to Phase 2 (FAULT-02) per CONTEXT.md, which will introduce a second call site (JMA station validation). If the executor finds the predicate hard to test inline, see the test strategy below — it tests the function-level reject behavior, not a private helper, so no extraction is needed.

    Per D-06, add three `#[test]` functions inside an `#[cfg(test)] mod tests` block at the end of `src/location.rs`. If a `mod tests` block already exists, append into it; otherwise create one. The tests target the validation predicate behavior through the existing `Error::LocationDetection` return surface:

    - `nan_coords_are_rejected`: construct a synthetic check by calling the predicate directly on `f64::NAN`. Since the predicate is inlined into detect_location(), the test instead asserts the f64 range-contains semantics that the guard relies on. Specifically: assert `!(-90.0..=90.0).contains(&f64::NAN)` and `!(-180.0..=180.0).contains(&f64::NAN)`. This pins the IEEE 754 ordering behavior so a future stdlib or refactor change is caught. Document inline: "Pins the IEEE 754 semantics detect_location() depends on (D-05, D-06)."

    - `infinite_coords_are_rejected`: same shape, using `f64::INFINITY` and `f64::NEG_INFINITY` for both lat and lon. Assert all four range-contains calls return `false`.

    - `out_of_range_coords_are_rejected`: assert `!(-90.0..=90.0).contains(&91.0_f64)` and `!(-180.0..=180.0).contains(&181.0_f64)`, plus the valid-side `(-90.0..=90.0).contains(&45.5_f64)` returns `true` (sanity anchor — confirms the predicate is not over-rejecting).
